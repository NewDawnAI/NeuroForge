# Running the demo brain at n=8192

Date: 2026-08-23
Binary: `build/neuroforge.exe`, mingw64
Base invocation: `--enable-learning --phase-c-seed=401 --sequential --demo-density=0.1`

## Result

n=8192 works now. It did not before.

| | before | after |
|---|---|---|
| n=8192, 20 steps | >900 s (killed, never completed) | **73 s** |
| n=4096, 1 step | >300 s (killed) | 5 s |
| n=2048, 1 step | 117 s | 2 s |

Final run: 16,384 neurons, **1,048,576 synapses**, 65,100,650 learning updates,
16,382/16,384 neurons active (100.0%), 73 s wall.

The synapse count is exactly `8192 x 64 x 2` — neurons per region, times
`max_per_source_cap`, times two directions. Density is irrelevant above
64/8192 = 0.0078, which is why 0.1 and 0.5 give the same number.

Getting there required fixing two O(N^2) defects. Neither was a tuning problem;
both were algorithmic.

## Defect 1: a global statistic recomputed on every weight update

`LearningSystem::updateStatistics(algorithm, weight_change)` is called once per
weight update, from 7 call sites (Hebbian, STDP, RewardModulated). It contained
a full traversal of every neuron in every region to recount `active_synapses`:

```cpp
// FIX: Update active synapses count by counting all synapses in the brain
if (brain_) {
    statistics_.active_synapses = 0;
    for (const auto& [region_id, region] : brain_->getRegions()) { ...
        for (const auto& neuron : region->getNeurons()) { ...
            statistics_.active_synapses += neuron->getInputSynapseCount();
```

Cost per step = O(synapses x neurons). At n=2048 that is roughly 900k updates
per step, each walking 4,096 neurons: **~3.7 billion neuron visits per step**,
all under `syn_state_mutex_`.

Measured slope before the fix:

| n | neurons | synapses | s/step |
|---|---|---|---|
| 1024 | 2,048 | 131,072 | 9.5 |
| 2048 | 4,096 | 262,144 | 39.5 |

4.2x cost for a 2x network — quadratic in neurons, while the synapse count only
doubled.

It is also unnecessary work. `active_synapses` counts synapses that *exist*, and
a weight update cannot change that. Moved to `refreshActiveSynapseCount()`,
called from `getStatistics()` on the read path. Same reported value, computed
once when someone asks for it.

After: 0.25 s/step at n=1024 (38x), 2.0 s/step at n=2048 (20x).

## Defect 2: "pre-reserve to avoid reallocation" forced a reallocation per insert

`Region::reserveInterRegionConnections(id, additional)` did:

```cpp
const std::size_t needed = vec.size() + additional;
if (vec.capacity() < needed) { vec.reserve(needed); }
```

`connectToRegion` calls it with `additional == 1` for every synapse. So capacity
was set to exactly `size + 1` each time, and the next `push_back` reallocated and
copied the entire vector. `inter_region_connections_` holds every synapse between
a region *pair* — 131,072 entries at n=1024 — so bulk insertion became O(n^2)
`shared_ptr` copies, each carrying an atomic refcount increment.

The comment said the function existed to avoid reallocation. It guaranteed one
per insert.

Fixed to grow geometrically (`reserve(max(needed, capacity * 2))`) in all three
helpers that shared the shape: `reserveInterRegionConnections`,
`reserveOutputConnections`, `reserveInputConnections`.

Construction time:

| n | before | after |
|---|---|---|
| 1024 | 5 s | 1 s |
| 2048 | 74 s | 2 s |
| 4096 | >300 s | 5 s |
| 8192 | (never reached) | 12 s |

Now approximately linear in synapse count, as it should be.

## Still O(n) per synapse: Region::getNeuron

`Region::getNeuron(NeuronID)` is a `std::find_if` linear scan over `neurons_`
under `region_mutex_`, and `connectToRegion` calls it twice per synapse. That is
still O(synapses x neurons) in construction.

It is no longer the bottleneck — after defect 2 was fixed, construction dropped
to roughly linear in practice — so it was left alone rather than fixed
speculatively. If construction becomes the limit again at larger n, an
id-to-index map on `Region` is the fix, and it must be kept in sync with
`createNeurons` and any growth or pruning path.

## Memory, and what it means for fruit-fly scale

Peak working set, measured:

| n | synapses | peak MB | bytes/synapse |
|---|---|---|---|
| 4096 | 524,288 | 334.8 | 669.7 |
| 8192 | 1,048,576 | 656.3 | 656.3 |

Linear, at **~657 bytes per synapse**. That is the binding constraint, and it is
heavy: a synapse is conceptually a source index, a target index and a weight
(~12 bytes). The overhead is the heap-allocated `Synapse` object plus the same
`shared_ptr` held in several vectors (`inter_region_connections_`,
`output_connections_`, `input_connections_`, and the neurons' own lists).

Against the adult fruit-fly connectome (~139,255 neurons, ~54.5M synapses, mean
fan-in ~390):

| | n=8192 now | fruit fly | ratio |
|---|---|---|---|
| neurons | 16,384 | ~139,255 | 11.8% |
| synapses | 1,048,576 | ~54.5M | 1.9% |
| fan-in | 64 (capped) | ~390 | 16% |

Extrapolating at 657 bytes/synapse, a fly-scale network needs **~36 GB** for the
synapses alone. Two things block fly scale, in order:

1. **Memory**, at ~657 bytes/synapse. This is the real limit and needs a leaner
   representation (indices into a flat arena rather than `shared_ptr` graphs),
   not more RAM.
2. **`max_per_source_cap = 64`** in `HypergraphBrain::connectRegions`, which
   holds fan-in to 64 regardless of density. Raising it to ~390 is a one-line
   change but multiplies synapse count, and therefore memory, by ~6.

Time is no longer the blocker: at 3 s/step for 1M synapses and roughly linear
scaling, fly scale projects to ~2.6 min/step, which is slow but tractable. It
was ~45 min/step before these fixes, on a network that could not be built.
